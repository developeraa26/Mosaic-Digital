# Ledger Plus Shop (v1.2.0)

**New in 1.2.0: F14, Zoho CRM sync (27 Nov 2026).** Every shop buyer and order now goes to the Zoho CRM module that the website forms already write to (**Ledgers Plus**, API name `Ledgers_Plus`), through the site's own Zoho connection: the "Elementor Pro Form Widget - Zoho CRM - Integration" add-on. No new keys are needed and the plugin never reads the add-on's tokens. **One record per person:** a buyer who is not in Zoho yet gets a record with Lead Status **Prospecting** when the order is placed, which becomes **Closed Opportunity** when the order is paid. A buyer who is already in Zoho (same email) keeps their record: it gets a note with the order and product details at checkout and a payment note, and its Lead Status becomes Closed Opportunity when the order is paid (it is never set back to Prospecting). For a paid order this happens **before the thank-you page is shown**, within 8 seconds. When Zoho is slow or down, the page is shown as usual and a background job finishes the sync, with retries after 5, 30 and 120 minutes. A new order action is **"Send to Zoho CRM again"**. Zoho's workflow rules run on every create and update. Details in section 1 (F14), the check list in section 7 ("After uploading 1.2.0"). 1.2.0 is a drop-in replacement for 1.1.2 (same folder and file) and contains everything from it.

**New in 1.1.2: F13, launch fixes (27 Nov 2026).** (a) The referral wording now carries the confirmed rules: "… you can receive AED 999 cash back after their payment is confirmed. No cash back is due if their order is refunded, cancelled or disputed." Until 1.1.1 the thank-you page and the My Account dashboard showed the placeholder "[Reward terms: to confirm]" to every buyer; reward terms with a part in [square brackets] are now left out of every page and email. (b) `/shop/` (page 885) and the product category, tag and attribute archives redirect (302) to the sales page 892 like the product page (F6): they rendered under the Elementor Pro archive template made for the blog. (c) The **Completed order** email now has "What happens next": Geidea's "Order status on success" is Completed on this site, so paid orders go from pending to completed and the Processing order email, the only one with the steps until 1.1.1, is never sent. Details in section 1 (F13), the check list in section 7 ("After uploading 1.1.2"). 1.1.2 is a drop-in replacement for 1.1.1 and 1.1.0 (same folder and file) and contains everything from them, including F12.

**New in 1.1.1: F12 Geidea payment safety net.** On 27 Nov 2026 a test card payment through Geidea succeeded, but WooCommerce orders 939 and 940 stayed "Pending payment" and the thank-you page offered "Pay" again. Geidea Online Payments 3.5.2 only changes the order status when Geidea's server-to-server callback reaches `https://ledgerplus.ae/?wc-api=geidea` and is accepted; for those orders nothing from Geidea was recorded at all. 1.1.1 (1) checks every Geidea callback, completes a correctly signed and matching paid order itself, refuses a signed "paid" callback that cannot belong to the order (wrong amount or currency, another site, a Geidea payment already recorded on another order) and records what the site answered Geidea, and (2) asks Geidea's API about unpaid Geidea orders when the callback does not arrive: on the thank-you page, in scheduled checks after checkout, and from a new "Check payment with Geidea" order action. Details in section 1 (F12), the client test plan in section 7, and how to re-check orders 939 and 940 in section 7 too. 1.1.1 is a drop-in replacement for 1.1.0 (same folder and file).

**New in 1.1.0: F11 email branding** (Ledger Plus look for the WooCommerce emails). Everything else works as in 1.0.0. Design notes, before/after screenshots and the email settings to apply: `../email/EMAIL-DESIGN.md`. 1.1.0 is a drop-in replacement: same folder and file (`ledgerplus-shop/ledgerplus-shop.php`), so upload it over 1.0.0.

These are the WooCommerce add-ons for selling the **E-Invoicing Starter Package** (product 890, AED 1,999 including 5% VAT) on ledgerplus.ae.

You can install the same code two ways. Use only one:

| File | What it is |
|---|---|
| `ledgerplus-shop/ledgerplus-shop.php` | The WordPress plugin. It is a single file. Put it in a folder called `ledgerplus-shop`, or zip that folder and upload it. |
| `ledgerplus-shop-wpcode.php` | The WPCode snippet. It is the same code, minus the plugin header and the HPOS compatibility declaration (the declaration needs a plugin file). It has no opening `<?php` tag. |
| `test/` | Local test harness: pure PHP (the Geidea callback test also uses PHP's built-in web server) and Node, with stubs of the WordPress and WooCommerce functions. |

Requirements: WordPress 6.5+, PHP 8.1+ (the site runs 8.4), WooCommerce 9.0+ (the site runs 11.3.1), and a **classic theme** (Hello Elementor). The source references below are to WooCommerce **11.3.1**.

Only an entry for exactly this order, with Success + Paid, the same amount and currency, a successful Pay transaction (when transactions are listed), for this site and not older than the order, counts as paid; failed or abandoned attempts are ignored; errors and time-outs never count as "not paid". **c) One completion routine** for all paths: per-order lock, order read again inside the lock, the same meta as Geidea writes (`Geidea Order Id` exactly as Geidea sent it, `Merchant Reference Id`, `Order Success Status Setting`), transaction id = Geidea order id, then `WC_Order::payment_complete()` with Geidea's success status (Completed on this site), and a note naming the source (Geidea callback, thank-you page check, scheduled check, manual check). So the order stays refundable through Geidea from WooCommerce, and F3 (referral code, emails) runs once. A **cancelled** order that Geidea reports paid (within 7 days) is completed with the note "payment confirmed by Geidea after the order was cancelled … refund it from this order if the sale should not go ahead". An order that was already paid once and later changed by hand is never completed again. | Order notes, the "Ledger Plus" box on the order screen (Geidea order id, this order's last callback, the site's last callback, and the last unverified ones when there are any), Order actions, WooCommerce → Status → Logs (`ledgerplus-geidea`) and → Scheduled Actions (`lp_shop_geidea_check`). |

### F13: launch fixes (1.1.2)

Confirmed by the client on 27 Nov 2026: AED 1,999 is a **yearly** price with **manual** renewal; refunds within 14 days if no e-invoices were sent; the referrer can receive AED 999 cash back when another business buys with their code and pays; no reward if the referred order is refunded, cancelled or disputed; no self-referral or same-group referral. The referral **payout method and timing are not confirmed**, so the plugin's texts promise neither. What the plugin already does for these rules is unchanged: a refunded or cancelled referred order voids the referral (F3c; a dispute or chargeback is not an order status, so a person handles it in the review); a self-referral by the same billing email or trade licence is refused or marked `ineligible_self` (F3c/F3d); a referral from another company of the same group cannot be recognised automatically and is left to the manual review of `pending_review` referrals. Renewal and the 14-day refund rule are handled by hand.

- **F13a, reward wording.** New defaults: `reward_text` = "you can receive AED 999 cash back after their payment is confirmed." and `reward_terms` = "No cash back is due if their order is refunded, cancelled or disputed." (`DEFAULT_REWARD_TEXT`, `DEFAULT_REWARD_TERMS`; `LP_SHOP_REWARD_TEXT`, `LP_SHOP_REWARD_TERMS` and the `lp_shop_settings` filter still override them). They make one paragraph after "When they buy Ledger Plus with your code, " on the thank-you page, the My Account dashboard, and the Processing and Completed order emails (branded card: the terms in grey after the reward text; plain text and the emails with `email_branding` off: one sentence). `LP_Shop::reward_terms_text()` leaves the terms out when they are empty or have any part in [square brackets] (such as the old "[Reward terms: to confirm]" or "Paid by [payment method] within [X days]."), on every page and in every email; then the sentence ends after the reward text, with no trailing space. 1.1.1 only hid such terms in the branded emails, and also hid the default terms, which would have hidden the new real default too. The reward text itself is used as given. The cart and checkout wording (F3g, F4) has no reward text and is unchanged. A scan of every string in the code finds no other "[… to confirm]" placeholder; the checkout foot block outside the plugin still has one (section 8).
- **F13b, shop archive redirect** (setting `redirect_shop_archive`, default `true`; constant `LP_SHOP_REDIRECT_SHOP_ARCHIVE`; filter `lp_shop_settings`). On `template_redirect` (priority 5, as F6) the shop page `/shop/` (page 885, the product post type archive, also product search results) and every product taxonomy archive (categories, tags, attributes) answer **302** to the sales page (`sales_page_id`, page 892 `/e-invoicing-starter/`), only while that page is published, keeping `utm_*`, `gclid`, `fbclid` and `msclkid`. Same guards as F6: not in the admin, AJAX, cron, REST, feeds, previews (`?preview`, `?preview_id`), the Customizer, embeds, `?add-to-cart`, `?elementor-preview`, and a shop manager (`manage_woocommerce`) stays with `?lp_stay=1`. Never redirected: cart, checkout (with its order-received and order-pay endpoints), My Account, the front page (a shop on the front page) and the sales page itself (no loop). F6 and F13b are separate settings. The "sales page itself" check compares `sales_page_id` with the shop page (`wc_get_page_id( 'shop' )`) on `/shop/` only: on a product category, tag or attribute archive `get_queried_object_id()` is a term id, counted apart from page ids, so a term that happens to have id 892 is redirected like any other.
- **F13c, "What happens next" in the Completed order email** (with `email_branding` on, as all F11 cards). The Completed order email (HTML and plain text) shows the steps card above the referral card, unless a Processing order email with the steps was already built for that order. The Processing order email records this in the order meta `_lp_next_steps_emailed` = `yes` (once; the HTML and plain-text parts of a multipart email and a resent Processing email find it set). A missing flag is checked once more in the database, in case the email's order object was read before another request saved it. The WooCommerce email preview (its dummy order has id 0) shows the steps in both emails and never writes; an order without an id is never written either. A Completed email resent from the admin shows the same as the first one (the Completed email never sets the flag). The referral card and the plain-text referral sentence are unchanged.

### F14: Zoho CRM sync (1.2.0)

**Asked by the client:** "connect this user info and product info into our Zoho CRM; if a purchase is complete, the lead status should be Closed Opportunity, otherwise Prospecting; if possible insert the values into the CRM before showing the final screen." **Decided on 27 Nov 2026:** one record per person (an existing record with the buyer's email is updated, not duplicated, and never moved down to Prospecting); Zoho's workflow rules must run on create and update.

**The connection.** The plugin uses the add-on the website forms already use: "Elementor Pro Form Widget - Zoho CRM - Integration" (itgalaxy, 1.21.0, folder `elementor-pro-form-widget-zoho-crm-integration`), class `Itgalaxy\Elementor\Form\Zoho\Integration\Includes\Crm`, its public static `sendGetRequest()`, `sendPostRequest()` and `sendPutRequest()` ( `$model`, `$fields` ). The add-on adds the access token (and refreshes it) and the API domain itself; this plugin never reads, logs or stores the add-on's tokens (`elementor-zohocrm-token`, `elementor-zohocrm-refresh-token`) or its API domain, and has no Zoho credentials of its own. The add-on writes each request (URL and fields) to its own log file `uploads/logs/elprozoho.log` when its logging is switched on; that is the add-on's behaviour, not this plugin's. When the add-on is not active (or a version without these three methods), nothing is sent and the order gets one note.

**When it runs.**
- **Checkout** (block checkout `woocommerce_store_api_checkout_order_processed`, classic `woocommerce_checkout_order_processed`, and "Pay for order" / classic through `woocommerce_payment_successful_result`): the plugin keeps the visitor's `utm_source`, `utm_medium`, `utm_campaign`, `utm_term` and `utm_keyword` from the add-on's cookie `elementor-zohocrm-utm-cookie` on the order (at most 255 characters each, once per order) and queues one background job (Action Scheduler, `as_enqueue_async_action( 'lp_shop_zoho_sync', { order_id, reason: checkout }, 'ledgerplus-shop' )`). Zoho is never called during "Place order", so the redirect to Geidea is not slowed down. Placing or paying the same order again ("Place order" or "Pay for order" once more) queues nothing once its checkout step is in Zoho or while a series of tries is under way, so a visitor cannot restart the retries. **Hourly limit:** the background job sends at most `zoho_open_per_hour` (60) unpaid orders without a known Zoho record per hour, site-wide; the others wait for the next hour (no attempt counted, no note; one info line in the log). Bots placing unpaid orders therefore cannot fill the CRM or use up the add-on's Zoho API credits, which the website forms share. Paid orders, the thank-you page and the order action are never limited.
- **Payment** (`woocommerce_order_status_changed` from an unpaid to a paid status, and `woocommerce_payment_complete`: WooCommerce's `payment_complete()`, Geidea's own handler, F12's completions, an order set to Processing or Completed by hand): another background job (reason `paid`). Zoho is never called inside Geidea's callback request (`?wc-api=geidea`) or any other server-to-server request.
- **Thank-you page** of a paid order (`template_redirect` priority 3, after F12's payment check at priority 1, before any output; only with the order's own key, like the page itself): when the order's "Closed Opportunity" step is not done yet, the sync runs right away with a time budget of `zoho_thankyou_budget` seconds (8) in all, each Zoho request at most `zoho_request_timeout` seconds (4; a filter on `http_request_args` that exists only while the plugin calls the add-on, and that also caps the add-on's token refresh at what is left of the budget). The search is not started with less than 1 second left; a write (create, Lead Status, note) only with its full `zoho_request_timeout` left, because a write cut off by the time-out has usually been carried out by Zoho all the same, and sending it again would add a second note or run the workflow rules once more. The order is read again for this (with HPOS, `wc_get_order()` would hand back the copy F12's check read earlier in the same request, from before Geidea's callback paid the order). The page is then shown; on a failure or time-out it is shown as usual, the error is kept on the order and a background job finishes the sync. At most one try per order every 30 seconds and 3 per order in an hour.
- **Order actions → "Send to Zoho CRM again"** (edit-order screen, users with `edit_shop_orders` or `manage_woocommerce`): the same sync right away (each request at most 10 s, 30 s in all); also for orders from before 1.2.0, for an order whose automatic tries ran out, and after the add-on was activated again. When everything is already in Zoho it only adds the note "nothing to send".
- Background jobs cap each Zoho request at 15 s (the add-on asks for 20 s).

**What one sync does** (`LP_Shop::zoho_sync_order()`: idempotent, one request at a time per order through an option lock `lp_shop_zlock_{order_id}`, the order and its meta read again inside the lock, each step saved as soon as Zoho confirmed it):
1. **Target:** "Closed Opportunity" (`zoho_status_paid`) when the order is paid (`wc_get_is_paid_statuses()`: processing, completed), otherwise "Prospecting" (`zoho_status_open`). Display values are sent, as the website forms do.
2. **Record:** the record id saved on the order; else `GET Ledgers_Plus/search?email=<billing email>` (Zoho answers HTTP 204 with no body when nothing matches; among several matches the record whose Email field is the address wins); else **create** the record. A create that Zoho refuses with `DUPLICATE_DATA` and the existing record's id counts as found. Only HTTP 204 means "no record": any other search answer without JSON (an error page from Zoho or a proxy, a body cut off, no HTTP status) is an error and nothing is created, so the person never gets a second record because of it (the add-on returns only the decoded body; the plugin reads the HTTP status through a filter on `http_response` that exists only while it calls the add-on). After a create that got no clear answer (time-out, connection lost, an answer without JSON, an error in the add-on), Zoho may have stored the record although its search does not show it yet: no second create is sent for 3 minutes; the next try, 5 minutes later, searches again and uses that record, or creates it when Zoho had not stored it.
3. **Create** (`POST Ledgers_Plus`, `"trigger": ["workflow"]`): `Name` (billing first and last name; else the company; else the email), `Email`, `Mobile`, `Lead_Status` (the target), `Lead_Source` "Website", `Lead_Form` "Ledger Plus Shop", `Owner` `{"id": "794156085"}`, `Description`, `Page_Name` "Checkout", `Landing_page_URL` (the checkout page URL), `Client_s_message` (the buyer's order note), and the five utm fields. Text fields are cut to 255 characters, the Description to 32,000. `Company1` is not used. The **Description** has one line each for: Client Company Name, Product (name, quantity and price incl. VAT), Order (number, total incl. VAT, payment method), Order date, Trade licence, VAT TRN, Referral code used (with the referrer order and its status), Possible existing customer, Buyer's own referral code, the buyer's order note, and "Sent by Ledger Plus Shop from the website checkout.". The filter `lp_shop_zoho_record_fields` ( `$fields`, `$order`, `$status` ) can change these fields; names that are not Zoho API names and values that are not text are dropped.
4. **Lead Status:** when the order is paid and the record is not "Closed Opportunity" from this order yet: `PUT Ledgers_Plus` with only `id` and `Lead_Status` "Closed Opportunity" (`"trigger": ["workflow"]`). An existing record's Lead Status is never set to Prospecting, and its Owner, Lead_Source, Lead_Form and Description are never changed.
5. **Notes** (`POST Notes`, `Parent_Id` = the record, `se_module` "Ledgers_Plus"), each once per order: **"Ledger Plus Shop order #N placed"** (date, order status, the same details as the Description) and, once paid, **"Ledger Plus Shop order #N paid"** (date paid, total, payment method, transaction id, order status, the Lead Status, product, referral code used, possible existing customer, the buyer's own referral code).
6. The order gets one note, for example "Ledger Plus: sent to Zoho CRM (Ledgers_Plus record 5725767000000412001): created as Prospecting; checkout note added (background job)." or "…: Lead Status set to Closed Opportunity; payment note added (thank-you page).".

So a typical order makes 3 Zoho requests at checkout (search, create, note) and 2 at payment (update, note); a buyer already in Zoho makes 2 and 2.

**Failures.** Every failed attempt of a background job or the order action adds an order note "Ledger Plus: Zoho CRM sync failed (attempt N of 4, background job): <reason>. <next step>", keeps the reason as the last error and counts the attempt; the next try is about **5, 30 and 120 minutes** later (`zoho_retry_delays`), after the 4th attempt the note says "No more automatic tries: use the order action "Send to Zoho CRM again"." The payment and the order action start a new series; the checkout job does only when no series is under way (placing the same order again does not restart one). A failure on the thank-you page adds no order note and counts no attempt; it is logged, and a background job (reason `retry`, so its failures count on from the attempts already made) is queued when none is waiting and the automatic tries are not used up: visiting the thank-you page again never starts a new series. What was done before an error is kept (a record created before a note failed is not created again). Reasons, as they appear in notes, the order box and the log:

| Reason | Meaning |
|---|---|
| `the "Elementor Pro Form Widget - Zoho CRM - Integration" add-on is not active …` | The add-on (its `Crm` class with the three methods) is not loaded. Noted once per order, not retried. Activate it, then use the order action. |
| `the Zoho CRM add-on is not connected to Zoho …` | The add-on has no access token and returned its own data instead of a Zoho answer. Reconnect the add-on in its own settings in the WordPress admin (the website forms need that too). Retried. |
| `the request to Zoho failed (<code>: <message>)` | A WordPress HTTP error or an error from the add-on's token refresh (for example `zoho_…` codes). Host names are shown as `[host]`. |
| `no answer from Zoho in time (cURL error 28 …)` | Zoho (or the network) did not answer within the request limit (15 s in a job, 4 s on the thank-you page). |
| `the time limit of 8 seconds ran out before the next Zoho request` | Thank-you page (or the order action's 30 s): too little time was left for the next request (the search needs 1 s, a write its full request time-out). The rest is done by the background job (logged as info on the thank-you page). |
| `unexpected answer from Zoho to the search (HTTP <code> / no HTTP status, no JSON)` | The search got an answer that is not Zoho's "no match" (HTTP 204) and has no JSON: an error page from Zoho or a proxy, a body cut off. Nothing is created (that could give the person a second record); retried. |
| `an earlier create got no answer from Zoho and the search does not show that record yet, so no second record is created within 3 minutes of it` | The previous create timed out or got no clear answer, and Zoho may have stored the record. Retried: the next try searches again and uses that record, or creates it when Zoho had not stored it. |
| `Zoho answered <CODE>: <message> (field <api_name>)` | Zoho's own error, for example `INVALID_TOKEN` or `OAUTH_SCOPE_MISMATCH` (the add-on's connection or its scopes), `INVALID_DATA (field Lead_Status)` (a picklist value does not exist), `MANDATORY_NOT_FOUND (field …)` (a field the module requires), `DUPLICATE_DATA` without a record id, `INVALID_MODULE` (the module name), `INTERNAL_ERROR`. |
| `…; the record <id> no longer exists in Zoho, so the next try looks the buyer up again` | Zoho answered `INVALID_DATA` for the record id of the Lead Status update or of a note (field `id` or `Parent_Id`, or no field and the message "the id given seems to be invalid"; the record was deleted or merged), or `RECORD_NOT_FOUND`. The plugin forgets it; the next try searches by email or creates a new record. |
| `unexpected answer from Zoho (empty / no data / no record id)` | Zoho's answer did not have the expected shape. |
| `the Zoho CRM add-on failed (<exception>: …)` / `Ledger Plus failed while preparing the request (…)` | A PHP error inside the add-on, or in this plugin or a `lp_shop_zoho_record_fields` filter. Retried like the others. |

Emails, phone numbers (also as digits only), the buyer's names, `Zoho-oauthtoken …` header values, long token-like strings, URLs and host names are hidden in these texts (`[email]`, `[phone]`, `[hidden]`, `[number]`, `[url]`, `[host]`). A job that finds another request sending the same order tries again 60 seconds later (not counted as an attempt; a checkout or paid job keeps its reason, so a payment's first failure still starts its own series).

**Order box.** The "Ledger Plus" box on the order screen shows "Zoho CRM record" (the record id, the module, and "created by this order", "existing record, found by email" or "existing record, reported by Zoho as a duplicate"; or "not sent yet", or "not sent: the Zoho CRM add-on is not active"), "Zoho CRM Lead Status sent" ("Closed Opportunity (time UTC)", "Prospecting (…)", "not changed (existing record; checkout note only)" or "none yet") and, when there is one, "Zoho CRM last error" (time, reason, failed attempts). The box now also appears on orders without product 890, with the Zoho lines only.

**Never breaks the shop.** Every entry point (checkout, payment hooks, the job, the thank-you page, the order action, the order box) catches every PHP error; checkout, payment, emails and the thank-you page go on as before. With `zoho_sync` off (or `define( 'LP_SHOP_ZOHO_SYNC', false );`) nothing is queued or sent and the Zoho lines and the order action are hidden.

It does **not** do the following: reward payouts, or anything else that moves money (F10); updating Zoho when an order is later cancelled or refunded (the record keeps Closed Opportunity; see section 8); the yearly renewal (there is no subscription, renewal order or reminder: renewal is manual). There is a marked `TODO - Phase 2` section at the end of the class.

    $s['geidea_lookups_per_hour'] = 60;   // thank-you page: at most N lookups per hour on the site (0 = none)

    $s['zoho_module']           = 'Ledgers_Plus';       // API name of the Zoho module (the website forms' module)
    $s['zoho_owner_id']         = '794156085';          // Owner of a new record (Zoho user id); '' = no Owner sent
    $s['zoho_status_open']      = 'Prospecting';        // Lead_Status of an unpaid order's new record (display value)
    $s['zoho_status_paid']      = 'Closed Opportunity'; // Lead_Status once the order is paid
    $s['zoho_lead_source']      = 'Website';            // Lead_Source of a new record ('' = not sent)
    $s['zoho_lead_form']        = 'Ledger Plus Shop';   // Lead_Form of a new record ('' = not sent)

The other keys are `product_id`, `sales_page_id`, `addon_product_id`, `phone_display`, `phone_tel`, `whatsapp_url`, `support_email` and `price_text` (`AED 1,999`). In reward texts, write apostrophes as ’ and not `'`: WooCommerce plain-text emails drop `&#039;`.

F12 reads the Geidea plugin's own settings (WooCommerce → Settings → Payments → Geidea): the environment (for the API host), the merchant public key and API password (for the signature and the API; never logged or stored by this plugin) and "Order status on success" (Completed on this site, used as the paid status so refunds through Geidea work). That setting must stay **Processing or Completed**: with any other value (On hold, or an unknown status) the callback guard leaves the status to Geidea's handler, and the lookups complete the order as Processing.

There are four extra filters:
- `lp_shop_block_coupon_labels`: the msgid → new text map for the block cart and checkout (F4).
- `lp_shop_email_css`: the F11 email CSS string (append rules to adjust the design).
- `lp_shop_zoho_record_fields` ( `$fields`, `$order`, `$status` ): the fields of a new Zoho record (F14), as Zoho API name → value (`Owner` as `array( 'id' => '…' )`). Return the array; other names and non-text values are dropped, text is cut to 255 characters (Description 32,000). Only used on create: an existing record is never changed except its Lead Status.
- `lp_shop_settings`: described above.

F14 uses the Zoho CRM add-on's connection and nothing else: no Zoho key, token or domain is set in this plugin. The module, field and picklist names above are the ones the website's hero form uses (Lead_Status "Prospecting" and "Closed Opportunity", Lead_Source "Website"). If a Lead_Status value is renamed in Zoho, set `zoho_status_open` / `zoho_status_paid` to the new display value.

## 3. Install

### Option 1: plugin (recommended)
1. Zip the folder `ledgerplus-shop/` (it contains `ledgerplus-shop.php`).
2. Go to **Plugins → Add New → Upload Plugin**, upload the zip and click **Activate**. The header has `Requires Plugins: woocommerce`, so WordPress only lets you activate it while WooCommerce is active.
3. The plugin declares itself compatible with HPOS and the cart and checkout blocks, so WooCommerce shows no compatibility warning.

### Option 2: WPCode snippet
1. Go to **Code Snippets → Add Snippet → Add Your Custom Code (New Snippet)** and choose Code Type **PHP Snippet**.
2. Paste the **whole** content of `ledgerplus-shop-wpcode.php` as it is. It deliberately has no `<?php` tag.
3. Set Insert Method to **Auto Insert** and Location to **Run Everywhere**, then save and **Activate**.
4. The snippet cannot declare HPOS compatibility. WooCommerce may list it as an "unknown" extension, which is harmless.

If both the plugin and the snippet are active, the second one to load does nothing (there is a `class_exists` guard) and nothing breaks. Still, deactivate the snippet once the plugin is installed.

## 4. Operator steps on the live site

Do these in this order. Steps 1-9 can be done while the store is still in "coming soon" mode.

1. **Install** the plugin (section 3, option 1). Then check **WooCommerce → Status → Logs**: there should be no `ledgerplus-shop` entries.

   - `woocommerce_checkout_phone_field` = `required`

17. **1.1.2 (F13):** contained in 1.2.0: upload `ledgerplus-shop-1.2.0.zip` ("Replace current with uploaded"); if the site still ran 1.1.0 or 1.1.1, also run the check list in section 7 ("After uploading 1.1.2").

**Which referrals can lead to a reward:** only an order whose `_lp_referral_status` is `pending_review` **and** whose order status is still processing or completed, after a person has reviewed it. `ineligible_self`, `void_cancelled` and `void_refunded` never do. A partly refunded order stays `pending_review` with a note, so a person decides.

Everything is written through `WC_Order` and `WC_Coupon` CRUD and the options API. There are no SQL queries. F14 sends the buyer's name, email, phone, company, trade licence, TRN, order note, order and product details and utm values to Zoho CRM (that is its purpose) and stores none of them anywhere else. Referral coupons are `shop_coupon` posts, which HPOS does not affect, so finding a coupon by its order uses `get_posts()` with a meta query.

## 8. Limits and things to know

- The repeat customer check matches the trade licence on HPOS (the site has HPOS on). On posts storage, it only checks the 20 most recent paid orders.
- The per-order lock is decided by the database (constant lock value), so two requests cannot both take a free lock. One case remains: a lock left by a request that died is cleared after 120 s, and if two requests clear it at the very same moment, both can end up working. For that case the plugin keeps the oldest referral coupon of the order, trashes the other, notes it, and both requests' emails show the kept code (tested in `run-race.php stale-worst`). Order notes can then appear twice.
- A payment hook waits up to 5 s (`lock_wait_seconds`) when another request is working on the same order. If it still cannot get the lock, it logs a warning and its email goes out without the code; the thank-you page and My Account still show it.
- The block wording (F4) and the referral error wording apply to **all** coupon codes, not only referral codes. This is fine because the shop uses coupons only for referrals. "Coupons" → "Referral code" was checked in the totals discount component only. Remove it through `lp_shop_block_coupon_labels` if the label ever shows up somewhere unexpected.
- WooCommerce stores coupon codes in lower case, so the applied-code chip in the cart and checkout shows `lp-xxxxxx`. The plugin's own messages, emails and pages show `LP-XXXXXX`. A CSS `text-transform: uppercase` on the chip would make them match.
- A TRN typed without any digit ("N/A", "pending") is saved as empty without an error message, because WooCommerce does not call the validator for an empty optional value.
- The trade licence is a required **contact** field, so logged-in customers must also fill it in under My Account → Account details (WooCommerce adds contact fields there).
- If a payment is confirmed only after the buyer has seen the thank-you page (for example a late webhook), the page says the code will follow. The code is created when the order becomes Processing and is in the Processing email.
- Local tests use PHP **8.3** CLI and stubs. They do not replace a staging test on WordPress 7.1.5, PHP 8.4 and WooCommerce 11.3.1. The code has no dynamic properties and no implicitly nullable typed parameters.
- When exactly WPCode runs "Run Everywhere" snippets was not checked. The code works whether it loads before or after `plugins_loaded` and `woocommerce_init`. It must load before `wp_loaded` for F5.
- Deactivating or deleting the plugin leaves the coupons and order meta in place, on purpose.
- **F12 sources.** The Geidea API facts come from docs.geidea.net search snippets (the pages could not be opened from here) and from Geidea's own plugin: the by-reference lookup is documented on the Egypt and KSA hosts; the UAE host `https://api.geidea.ae` is the one Geidea's UAE `config.php` uses for its refund and config calls on the same `/pgw/api/v1` path. The empty / not-found answer is not documented. The code therefore reads the answer defensively and fails safe: only an exact match (reference, Success + Paid, amount, currency, a successful Pay transaction when listed, this site, not older than the order) completes an order; everything else leaves it unchanged. Set `geidea_api_base` if Geidea gives another host.
- **F12 does not repair Geidea's callback.** When the callback is refused or never arrives, Geidea's own handler still does nothing for that order; the safety net completes it from the thank-you page or a scheduled check instead, and the note/log says what Geidea's callback got. Whether Geidea retries a refused callback (including the 400 the plugin causes when it refuses one) is not documented.
- **Re-split callbacks (Geidea's signature scheme).** Geidea signs the order number and the time stamp joined with no separator, so someone holding a genuine signed callback body (from a log, or a staging site on the same merchant account) can make it name another order number. The plugin refuses such a body when the amount, currency or site differ or when that Geidea payment is already on another order, and it never completes one itself without a recent, well-formed time stamp or Geidea's API confirming the payment. One case remains: a callback that was never processed, re-split onto another unpaid order with the same total while Geidea's API cannot be asked, is still completed by Geidea's own handler (the plugin's note on that order says it could not confirm the callback). Only Geidea can close this (a separator or a signed order number). The time stamp check assumes Geidea sends `11/27/2026 07:55:01`-style or ISO 8601 stamps; any other shape makes the guard ask Geidea's API first (up to 5 s more before the reply).
- **Anyone can POST to the callback URL.** Such requests never change an order. They are noted as "Unverified Geidea callback" (max 3 notes per order, no free text from the request), kept on their own lines in the admin box, and logged at most 60 times an hour, so they cannot hide or replace Geidea's own callbacks.
- **Scheduled checks are not capped site-wide:** each Geidea order can cause 4 API calls (one per scheduled check, fewer once it is paid), in addition to at most 3 thank-you page lookups per order and 60 per hour on the site.
- The `wp_php_error_args` filter (used to keep the fatal error WordPress's handler saw) is WordPress core code that is not in the local source copy; without it, the recorder still reads `error_get_last()` first, before any other shutdown callback.
- Geidea's own handler runs after the plugin completed the order and calls `woocommerce_pre_payment_complete` and `woocommerce_payment_complete` a second time (it always did, once). No status hook or email fires again; stock is reduced only once per order (WooCommerce keeps a per-order "stock reduced" flag; that code is not in the local source copy). Geidea's handler has no amount check of its own, so when a signed "paid" callback does not match the order (amount, currency, site, Geidea payment already on another order) the plugin stops that handler for the request and WooCommerce answers 400; the order is left unpaid and the note says why.
- When Geidea's callback names an order number that does not exist, Geidea's handler stops with a PHP fatal error (500); the log line shows it (seen in the local test with a copy of its code).
- The thank-you page check can delay that page by up to `geidea_lookup_timeout` (10 s) when Geidea's API is slow, once per order every 20 s.
- Scheduled checks need WP-Cron / Action Scheduler to run. They stop after 120 minutes; later, use the order action.
- Two paid Geidea payments for one order (two Place order clicks, both paid): the order is completed with the first and a note asks to check for a double charge.
- An order that was paid once and later set to cancelled, failed or on-hold by hand is never completed again by the plugin, and a cancelled order older than `geidea_max_age_days` (7) is only reported, not completed.
- The payment lock has the same residual case as the referral lock (two requests clearing a stale lock at the very same moment). The order is read again inside the lock and carries `_lp_geidea_paid` once completed, which keeps a second completion out in every other case. With HPOS's optional "data store caching" feature (off by default) a re-read could still come from cache; the site does not use it as far as known.

- **F13c and orders from before 1.1.2:** a Processing email built before 1.1.2 set no flag, so when such an order is completed later, its Completed email shows the steps again. Paid Geidea orders on this site skip Processing, so this only concerns orders paid another way (for example a bank transfer set to Processing by hand).
- **F13c flag = email built:** `_lp_next_steps_emailed` says that WooCommerce built a Processing email with the steps to send it, not that it was delivered. With `email_branding` off no email has the steps (as in 1.0.0) and no flag is written.
- **F13b scope:** product search results (`?s=…&post_type=product`) belong to the shop archive and redirect too, and WooCommerce's own links to the shop page ("Return to shop" on an empty cart, breadcrumbs) now end on the sales page. The Elementor Pro archive template keeps its display conditions; while the redirect is on it is just never reached for product archives. A page cache can keep serving an old `/shop/` page until it is purged.
- **F13a:** only the reward **terms** are checked for placeholders; the reward text is used exactly as set, so keep it a complete phrase ending with a full stop (apostrophes as ’).
- **Placeholders outside the plugin:** the checkout foot block (`../pages/blocks/checkout-foot.html`, operator step 5) has "[Tax invoice by email: to confirm]" (`span.lp-shop-tbc`); if it was pasted as supplied, the live checkout page 887 shows it. The plugin cannot change it: edit page 887. `../pages/purchase-page-builder.py` also still has "[… to confirm]" texts for the sales page (one-time or yearly, refund policy, payout, login timing) and "you get AED 999 cash back", some of which the client has now confirmed. Step 7 of "After uploading 1.1.2" (section 7) says what to replace them with on the live pages; the two source files still have to be brought in line.

- **F14, one record per person by email:** the search uses the order's billing email. A person who bought with another email than the one in Zoho gets a second record. A record created seconds earlier by a website form may not be found by Zoho's search yet; if the module has a duplicate check on Email, Zoho answers `DUPLICATE_DATA` with that record's id and the plugin uses it, otherwise a second record is possible.
- **F14, refunds and cancellations are not sent to Zoho:** the record keeps Closed Opportunity and the payment note. A refunded or cancelled order has to be changed in Zoho by hand (see the `TODO - Phase 2` comment).
- **F14, a request that timed out may still have reached Zoho:** when Zoho created a record or a note but its answer did not arrive in time, the plugin cannot know it. A record: no second create is sent for 3 minutes, and the next try (5 minutes later) finds it by email; only when Zoho's search still does not show it then, a second record is possible. A note can be added twice. On the thank-you page a write only starts with its full 4 s left, which makes a cut-off write rare there.
- **F14, thank-you page time:** the page can take up to `zoho_thankyou_budget` (8 s) longer when Zoho is slow, once per order every 30 s; together with F12's payment check (only for Geidea orders that are not paid yet: the lookup up to 10 s, plus up to 5 s waiting for the lock when Geidea's callback is completing the same order, then the Processing / Completed email sent in that request) the worst case is about 23 s plus the email. Set `zoho_thankyou_budget` to 0 to leave the sync to the background job only (it then usually runs within a minute, with WP-Cron).
- **F14, the add-on's own log:** with its logging switched on, the Zoho CRM add-on writes every request, including the buyer's details, to `uploads/logs/elprozoho.log`. That is the add-on's setting.
- **F14, Description is written once:** an existing record's Description is never changed; each order's details are in its own Zoho notes. The Description of a new record shows the order as it was when the record was created (for example "Possible existing customer: Checked when payment is confirmed" for an unpaid order).
- **F14 and the referral rules:** the notes show the referral code used and its status at that moment (`pending review`, `ineligible`…). A later void (refund, cancellation) is not sent.
- **F14, hourly limit of unpaid orders:** with more than `zoho_open_per_hour` (60) unpaid orders an hour (a sale, or bots), the others reach Zoho in the following hours, 60 an hour. Raise the setting (up to 1000) or set 0 for no limit. Against checkout bots, also consider WooCommerce's Store API rate limiting (filter `woocommerce_store_api_rate_limit_options`).
- **F14 and HPOS order saves:** each Zoho step saves order meta; with HPOS, WooCommerce may then save the order itself (`date_modified`, `woocommerce_update_order`, `order.updated` webhooks). No status hook runs and nothing else of the order is written.
- **F14 needs WP-Cron / Action Scheduler** for the background jobs and retries, like F12. Deactivating the plugin cancels the pending jobs; use the order action for those orders afterwards.
- **F14 sources:** the add-on's `Crm` methods and their behaviour come from the add-on's code as read on the live site (brief of 27 Nov 2026); the token refresh inside `RequestHelper::getAuthInfo()` was not readable. The Zoho answers modelled in the tests (success items, `DUPLICATE_DATA` with `details.id`, `INVALID_DATA` with `details.api_name`, top-level errors, HTTP 204 for a search without match) follow the Zoho CRM v2 API; the live module was not called from here. The first live test (section 7) is the real check.
