# Ledger Plus Shop (v1.1.1)

**New in 1.1.1: F12 Geidea payment safety net.** On 27 Nov 2026 a test card payment through Geidea succeeded, but WooCommerce orders 939 and 940 stayed "Pending payment" and the thank-you page offered "Pay" again. Geidea Online Payments 3.5.2 only changes the order status when Geidea's server-to-server callback reaches `https://ledgerplus.ae/?wc-api=geidea` and is accepted; for those orders nothing from Geidea was recorded at all. 1.1.1 (1) checks every Geidea callback, completes a correctly signed and matching paid order itself, refuses a signed "paid" callback that cannot belong to the order (wrong amount or currency, another site, a Geidea payment already recorded on another order) and records what the site answered Geidea, and (2) asks Geidea's API about unpaid Geidea orders when the callback does not arrive: on the thank-you page, in scheduled checks after checkout, and from a new "Check payment with Geidea" order action. Details in section 1 (F12), the client test plan in section 7, and how to re-check orders 939 and 940 in section 7 too. 1.1.1 is a drop-in replacement for 1.1.0 (same folder and file).

**New in 1.1.0: F11 email branding** (Ledger Plus look for the WooCommerce emails). Everything else works as in 1.0.0. Design notes, before/after screenshots and the email settings to apply: `../email/EMAIL-DESIGN.md`. 1.1.0 is a drop-in replacement: same folder and file (`ledgerplus-shop/ledgerplus-shop.php`), so upload it over 1.0.0.

These are the WooCommerce add-ons for selling the **E-Invoicing Starter Package** (product 890, AED 1,999 including 5% VAT) on ledgerplus.ae.

You can install the same code two ways. Use only one:

| File | What it is |
|---|---|
| `ledgerplus-shop/ledgerplus-shop.php` | The WordPress plugin. It is a single file. Put it in a folder called `ledgerplus-shop`, or zip that folder and upload it. |
| `ledgerplus-shop-wpcode.php` | The WPCode snippet. It is the same code, minus the plugin header and the HPOS compatibility declaration (the declaration needs a plugin file). It has no opening `<?php` tag. |
| `test/` | Local test harness: pure PHP (the Geidea callback test also uses PHP's built-in web server) and Node, with stubs of the WordPress and WooCommerce functions. |

Requirements: WordPress 6.5+, PHP 8.1+ (the site runs 8.4), WooCommerce 9.0+ (the site runs 11.3.1), and a **classic theme** (Hello Elementor). The source references below are to WooCommerce **11.3.1**.

| F3e | **Possible existing customer:** when another paid order has the same billing email or trade licence, the order gets the note "Possible existing customer: order #X" and the meta `_lp_possible_repeat=yes`. | Order notes. |
| F3f | The **admin "New order" email** gets a short "Ledger Plus checks" block: trade licence, TRN, referral code used (with the referrer order number and status), the possible repeat flag, and the buyer's own new code. | F5 | Opening `/checkout/?add-to-cart=890` when product 890 is already in the cart shows **no** "You cannot add another…" error. The checkout simply opens. | Buy buttons on the sales page. |
| F6 | The product 890 page redirects (302) to sales page 892, but **only once page 892 is published**. | `/product/...` URL of product 890. |
| F7 | A "What happens next" block on the thank-you page, with three steps and the help line "Need help? Call or WhatsApp +971 50 342 0832.". It makes no time promises. What shows depends on the order status: **paid**: the steps and the buyer's code; **pending or on-hold**: the steps introduced by "Once your payment is confirmed:" and "Your referral code will appear here and in your confirmation email once your payment is confirmed."; **failed, cancelled or refunded**: only the help line. | Thank-you page. |
| F11 | **Email branding** (setting `email_branding`, default on). WooCommerce keeps its own email templates. The plugin (1) adds Ledger Plus CSS through `woocommerce_email_styles`, which WooCommerce inlines with Emogrifier like its own CSS: blue top edge, navy headings, a cleaner order table, a navy footer, mobile sizes; (2) prints its own cards from `woocommerce_email_order_meta`: "What happens next" (Processing order email), "Your referral code" with the code large (Processing and Completed order emails), "Ledger Plus checks" as a label/value table (New order and "Payment confirmed" admin emails); (3) hides WooCommerce's grey placeholder thumbnail when no ordered product has an image (`woocommerce_email_order_items_args`); (4) keeps every line of the sent message within 998 characters (`woocommerce_mail_content`: line breaks in the `<style>` element and before block-level tags in over-long lines; no visual change); (5) on WooCommerce → Settings → Emails, warns when WooCommerce's new email templates are off, because the CSS needs them (`admin_notices`). Brand colours are fixed by the plugin; the font follows WooCommerce's Font family setting. In the WooCommerce email preview (Settings → Emails), whose dummy order has no Ledger Plus product, the cards show the sample code `LP-SAMPLE`. Plain-text emails get the steps as text. The CSS is only added when WooCommerce's "email improvements" templates are on, and never to block-editor emails. With `email_branding` off, the emails are byte for byte those of 1.0.0. | All WooCommerce emails (CSS); Processing, Completed, New order and "Payment confirmed" emails (cards). |
| F12 | **Geidea payment safety net** (setting `geidea_safety_net`, default on; only orders paid with the `geidea` gateway). **a) Callback guard:** on `?wc-api=geidea` POSTs, before Geidea's own handler, the plugin reads the body (max 256 KB), finds the order from `merchantReferenceId`, and verifies the signature exactly as Geidea does (HMAC-SHA256 with the API password, compared timing-safe). For a valid Success + Paid callback whose amount and currency match an unpaid order, it completes the order itself (c) once the callback is shown to belong to this order: its time stamp is a recent date (`11/27/2026 07:55:01` style or ISO 8601), or else Geidea's API lists the same Geidea payment as paid for this order. (Geidea's signature joins the order number and the time stamp with no separator, so a genuine signed body can be re-split to name another order number; a re-split always breaks the time stamp.) Geidea's handler then runs as usual (it finds the order already Completed, so no status hook or email fires twice, and it still saves its card token and meta). Geidea's handler marks any signed Success + Paid callback paid, whatever the amount, so the plugin **stops it** (WooCommerce then answers Geidea 400) when such a callback cannot belong to the order: the amount or currency differs, it was made for another site, or its Geidea payment is already recorded on another order. During a callback, Geidea's handler also cannot move a paid order back to an unpaid status. At the end of the request the plugin records what went back to Geidea, e.g. "Geidea callback: Success / Paid, Geidea order …, AED 1.00. Signature OK. Ledger Plus completed the order (now Completed). Site reply: 200 Order is completed! (Order status now: Completed.)", or "… Site reply: 500 … PHP fatal error: … (file:line)". Callbacks with a valid signature get an order note each (max 10 per order) and the "last callback" lines. Anything else (anyone can POST to that URL) is kept apart as "Unverified Geidea callback", max 3 notes per order, its own "last unverified" lines, no free text from the request, and at most 60 log lines an hour. **b) Asking Geidea** (`GET https://api.geidea.ae/pgw/api/v1/direct/order?MerchantReferenceId=<order id>`, Basic auth, 10 s timeout) when the callback never arrives: on the thank-you page (valid order key only, unpaid Geidea orders up to 7 days old, at most once per order every 20 s, 3 times per order in an hour and 60 times an hour for the site), in scheduled checks 2, 10, 30 and 120 minutes after checkout, also after "Pay for order" (Action Scheduler; once the order is paid the remaining checks are cancelled, and deactivating the plugin cancels all of them), and from **Order actions → "Check payment with Geidea"** on the edit-order screen (the result is an order note; when Geidea's API answers with an error, the note quotes Geidea's code and message, the start of the page, or the host it redirects to). Only an entry for exactly this order, with Success + Paid, the same amount and currency, a successful Pay transaction (when transactions are listed), for this site and not older than the order, counts as paid; failed or abandoned attempts are ignored; errors and time-outs never count as "not paid". **c) One completion routine** for all paths: per-order lock, order read again inside the lock, the same meta as Geidea writes (`Geidea Order Id` exactly as Geidea sent it, `Merchant Reference Id`, `Order Success Status Setting`), transaction id = Geidea order id, then `WC_Order::payment_complete()` with Geidea's success status (Completed on this site), and a note naming the source (Geidea callback, thank-you page check, scheduled check, manual check). So the order stays refundable through Geidea from WooCommerce, and F3 (referral code, emails) runs once. A **cancelled** order that Geidea reports paid (within 7 days) is completed with the note "payment confirmed by Geidea after the order was cancelled … refund it from this order if the sale should not go ahead". An order that was already paid once and later changed by hand is never completed again. | Order notes, the "Ledger Plus" box on the order screen (Geidea order id, this order's last callback, the site's last callback, and the last unverified ones when there are any), Order actions, WooCommerce → Status → Logs (`ledgerplus-geidea`) and → Scheduled Actions (`lp_shop_geidea_check`). |

It does **not** do the following: Zoho CRM sync, reward payouts, or anything else that moves money (F10). There is a marked `TODO - Phase 2` section at the end of the class.

## 2. Settings (F8)

The defaults live at the top of the `LP_Shop` class. There are two ways to change them without editing the code.

**A. Constants in `wp-config.php`** (above "That's all, stop editing"):

| Constant | Default |
|---|---|
| `LP_SHOP_PRODUCT_ID` | `890` |
| `LP_SHOP_SALES_PAGE_ID` | `892` |
| `LP_SHOP_ADDON_PRODUCT_ID` | `891` |
| `LP_SHOP_PHONE_DISPLAY` | `+971 50 342 0832` |
| `LP_SHOP_PHONE_TEL` | `+971503420832` |
| `LP_SHOP_WHATSAPP_URL` | `https://wa.me/971503420832` |
| `LP_SHOP_REWARD_TEXT` | `you get AED 999 cash back after their payment is confirmed.` |
| `LP_SHOP_REWARD_TERMS` | `[Reward terms: to confirm]` |
| `LP_SHOP_GEIDEA_SAFETY_NET` | `true` (F12; `define( 'LP_SHOP_GEIDEA_SAFETY_NET', false );` is the emergency off switch, see section 7 step 8) |

**B. The `lp_shop_settings` filter** (for example in a small WPCode snippet):

```php
add_filter( 'lp_shop_settings', function ( $s ) {
    $s['reward_terms']          = 'One reward per referred company. Paid by bank transfer within 14 days.';
    $s['redirect_product_page'] = true;   // F6 on/off
    $s['relabel_coupons']       = true;   // F4 + referral wording of coupon errors on/off
    $s['require_paid_referrer'] = true;   // F3d: refuse codes whose referrer order is refunded/cancelled
    $s['admin_paid_notice']     = true;   // F3f: "Payment confirmed" admin email for on-hold orders
    $s['lock_wait_seconds']     = 5;      // F3a: how long a payment hook waits for another request (0-10)
    $s['email_branding']        = true;   // F11: Ledger Plus email design (false = the 1.0.0 emails)
    $s['buy_now_product_ids']   = array( 890, 891 ); // F5 applies to these (only if "Sold individually")
    // F12 Geidea payment safety net:
    $s['geidea_safety_net']       = true;                    // false = callbacks handled by Geidea alone, as in 1.1.0
    $s['geidea_check_delays']     = array( 2, 10, 30, 120 ); // minutes after checkout; array() = no scheduled checks
    $s['geidea_lookup_timeout']   = 10;   // seconds to wait for Geidea's API (3-30)
    $s['geidea_lookup_interval']  = 20;   // thank-you page: at most one lookup per order every N seconds
    $s['geidea_lookups_per_order_hour'] = 3; // thank-you page: at most N lookups per order in an hour (1-60)
    $s['geidea_lookups_per_hour'] = 60;   // thank-you page: at most N lookups per hour on the site (0 = none)
    $s['geidea_max_age_days']     = 7;    // older orders are not checked automatically; older cancelled orders are never completed
    $s['geidea_api_base']         = '';   // '' = from the Geidea plugin's environment (UAE-PROD: https://api.geidea.ae)
    return $s;
} );
```

The other keys are `product_id`, `sales_page_id`, `addon_product_id`, `phone_display`, `phone_tel`, `whatsapp_url`, `support_email` and `price_text` (`AED 1,999`). In reward texts, write apostrophes as ’ and not `'`: WooCommerce plain-text emails drop `&#039;`.

F12 reads the Geidea plugin's own settings (WooCommerce → Settings → Payments → Geidea): the environment (for the API host), the merchant public key and API password (for the signature and the API; never logged or stored by this plugin) and "Order status on success" (Completed on this site, used as the paid status so refunds through Geidea work). That setting must stay **Processing or Completed**: with any other value (On hold, or an unknown status) the callback guard leaves the status to Geidea's handler, and the lookups complete the order as Processing.

There are three extra filters:
- `lp_shop_block_coupon_labels`: the msgid → new text map for the block cart and checkout (F4).
- `lp_shop_email_css`: the F11 email CSS string (append rules to adjust the design).
- `lp_shop_settings`: described above.

## 3. Install

### Option 1: plugin (recommended)
1. Zip the folder `ledgerplus-shop/` (it contains `ledgerplus-shop.php`).
2. Go to **Plugins → Add New → Upload Plugin**, upload the zip and click **Activate**. The header has `Requires Plugins: woocommerce`, so WordPress only lets you activate it while WooCommerce is active.
3. The plugin declares itself compatible with HPOS and the cart and checkout blocks, so WooCommerce shows no compatibility warning.

### Option 2: WPCode snippet
1. Go to **Code Snippets → Add Snippet → Add Your Custom Code (New Snippet)** and choose Code Type **PHP Snippet**.
2. Paste the **whole** content of `ledgerplus-shop-wpcode.php` as it is. It deliberately has no `<?php` tag.
3. Set Insert Method to **Auto Insert** and Location to **Run Everywhere**, then save and **Activate**.
4. The snippet cannot declare HPOS compatibility. WooCommerce may list it as an "unknown" extension, which is harmless.

If both the plugin and the snippet are active, the second one to load does nothing (there is a `class_exists` guard) and nothing breaks. Still, deactivate the snippet once the plugin is installed.

## 4. Operator steps on the live site

Do these in this order. Steps 1-9 can be done while the store is still in "coming soon" mode.

1. **Install** the plugin (section 3, option 1). Then check **WooCommerce → Status → Logs**: there should be no `ledgerplus-shop` entries.
2. **WooCommerce → Settings → General → Currency position: "Left with space"**. This shows "AED 1,999.00" instead of "AED1,999.00".
3. **Checkout field options** (WooCommerce 11.3.1 reads these options, not block attributes; see `blocks/checkout-options-note.md`). Set both to the plain string `required`:
   - `woocommerce_checkout_company_field` = `required`
   - `woocommerce_checkout_phone_field` = `required`
4. **Product 890 → Inventory → "Sold individually"** must stay ticked (F5 relies on it). If product 891 is published later, tick it there too, or F5 does nothing for it.
5. **Checkout page 887** (block editor, or the code editor). Keep the `woocommerce/checkout` block and add:
   - **above** `<!-- wp:woocommerce/checkout ...-->`: a Custom HTML block with the content of `blocks/checkout-head.html` (heading "Complete your order", "It takes about 2 minutes.", the referral help text and the help line), written as `<!-- wp:html -->` + the file content + `<!-- /wp:html -->`;
   - **below** `<!-- /wp:woocommerce/checkout -->`: a Custom HTML block with the content of `blocks/checkout-foot.html` (the trust lines; keep "[payment gateway]" until the gateway is chosen);
   - **inside** the Checkout block: replace the `woocommerce/checkout-actions-block` comment with `<!-- wp:woocommerce/checkout-actions-block {"placeOrderButtonLabel":"Pay securely"} -->` `<div class="wp-block-woocommerce-checkout-actions-block"></div>` `<!-- /wp:woocommerce/checkout-actions-block -->`, keeping any attributes it already has (details in `blocks/checkout-actions-note.md`).
6. **Cart page 886**: a Custom HTML block with `blocks/cart-head.html` **above** the `woocommerce/cart` block.
7. **My Account page 888**: a Custom HTML block with `blocks/account-head.html` **above** the `[woocommerce_my_account]` shortcode block.
8. **Appearance → Customize → Additional CSS**: add `store.css` after any CSS already there (saving replaces the whole Additional CSS). It also styles the plugin's thank-you and My Account classes (store.css section 15). The Customizer checker (CSSLint 1.0.4) reports `:is()`, `:has()` and `@container` as errors although the CSS is valid; tick "Update anyway" to save, or save it with `wp_update_custom_css_post()` from WP-CLI.
9. **WooCommerce → Settings → Emails**: keep **New order** enabled with the right recipient (F3f and the "Payment confirmed" notice use it), and keep **Processing order** and **Completed order** enabled (they carry the buyer's code). Install an SMTP plugin before launch so these emails arrive.
10. **Payment gateway**: install the WooCommerce Stripe extension or WooPayments, test it in test mode, then replace "[payment gateway]" in the checkout foot block with its name, and check that the gateway does not replace the "Pay securely" label.
11. **Reward terms**: when agreed, set `LP_SHOP_REWARD_TERMS` in `wp-config.php` (or the `lp_shop_settings` filter) to replace "[Reward terms: to confirm]". Until then the 1.1.0 emails leave the placeholder out, but the thank-you page and My Account still show it.
12. **Coupons**: keep coupons enabled (they are). Do not create other coupons: the cart and checkout call every coupon a "referral code". Do not edit the `LP-` coupons by hand.
13. **Publish page 892** when ready. The product page redirect starts by itself. A shop manager can still see the product page at `…/product/…/?lp_stay=1`.
14. Run the staging test plan (section 7) with a test gateway, then switch the store from "coming soon" to live (**WooCommerce → Settings → Site visibility → Live**).
15. Keep a **classic theme**.
16. **1.1.1 (F12, Geidea):** upload `ledgerplus-shop-1.1.1.zip` over 1.1.0 ("Replace current with uploaded"), then run the client test plan in section 7 ("After uploading 1.1.1"), including the re-check of orders 939 and 940. WP-Cron must run for the scheduled checks (WooCommerce → Status → Scheduled Actions shows whether actions run on time). On a block theme, the order-received page uses the Order Confirmation template instead of `checkout/thankyou.php`, so the F3b and F7 thank-you blocks would not show.

Everything is written through `WC_Order` and `WC_Coupon` CRUD and the options API. There are no SQL queries. Referral coupons are `shop_coupon` posts, which HPOS does not affect, so finding a coupon by its order uses `get_posts()` with a meta query.

## 8. Limits and things to know

- The repeat customer check matches the trade licence on HPOS (the site has HPOS on). On posts storage, it only checks the 20 most recent paid orders.
- The per-order lock is decided by the database (constant lock value), so two requests cannot both take a free lock. One case remains: a lock left by a request that died is cleared after 120 s, and if two requests clear it at the very same moment, both can end up working. For that case the plugin keeps the oldest referral coupon of the order, trashes the other, notes it, and both requests' emails show the kept code (tested in `run-race.php stale-worst`). Order notes can then appear twice.
- A payment hook waits up to 5 s (`lock_wait_seconds`) when another request is working on the same order. If it still cannot get the lock, it logs a warning and its email goes out without the code; the thank-you page and My Account still show it.
- The block wording (F4) and the referral error wording apply to **all** coupon codes, not only referral codes. This is fine because the shop uses coupons only for referrals. "Coupons" → "Referral code" was checked in the totals discount component only. Remove it through `lp_shop_block_coupon_labels` if the label ever shows up somewhere unexpected.
- WooCommerce stores coupon codes in lower case, so the applied-code chip in the cart and checkout shows `lp-xxxxxx`. The plugin's own messages, emails and pages show `LP-XXXXXX`. A CSS `text-transform: uppercase` on the chip would make them match.
- A TRN typed without any digit ("N/A", "pending") is saved as empty without an error message, because WooCommerce does not call the validator for an empty optional value.
- The trade licence is a required **contact** field, so logged-in customers must also fill it in under My Account → Account details (WooCommerce adds contact fields there).
- If a payment is confirmed only after the buyer has seen the thank-you page (for example a late webhook), the page says the code will follow. The code is created when the order becomes Processing and is in the Processing email.
- Local tests use PHP **8.3** CLI and stubs. They do not replace a staging test on WordPress 7.1.5, PHP 8.4 and WooCommerce 11.3.1. The code has no dynamic properties and no implicitly nullable typed parameters.
- When exactly WPCode runs "Run Everywhere" snippets was not checked. The code works whether it loads before or after `plugins_loaded` and `woocommerce_init`. It must load before `wp_loaded` for F5.
- Deactivating or deleting the plugin leaves the coupons and order meta in place, on purpose.
- **F12 sources.** The Geidea API facts come from docs.geidea.net search snippets (the pages could not be opened from here) and from Geidea's own plugin: the by-reference lookup is documented on the Egypt and KSA hosts; the UAE host `https://api.geidea.ae` is the one Geidea's UAE `config.php` uses for its refund and config calls on the same `/pgw/api/v1` path. The empty / not-found answer is not documented. The code therefore reads the answer defensively and fails safe: only an exact match (reference, Success + Paid, amount, currency, a successful Pay transaction when listed, this site, not older than the order) completes an order; everything else leaves it unchanged. Set `geidea_api_base` if Geidea gives another host.
- **F12 does not repair Geidea's callback.** When the callback is refused or never arrives, Geidea's own handler still does nothing for that order; the safety net completes it from the thank-you page or a scheduled check instead, and the note/log says what Geidea's callback got. Whether Geidea retries a refused callback (including the 400 the plugin causes when it refuses one) is not documented.
- **Re-split callbacks (Geidea's signature scheme).** Geidea signs the order number and the time stamp joined with no separator, so someone holding a genuine signed callback body (from a log, or a staging site on the same merchant account) can make it name another order number. The plugin refuses such a body when the amount, currency or site differ or when that Geidea payment is already on another order, and it never completes one itself without a recent, well-formed time stamp or Geidea's API confirming the payment. One case remains: a callback that was never processed, re-split onto another unpaid order with the same total while Geidea's API cannot be asked, is still completed by Geidea's own handler (the plugin's note on that order says it could not confirm the callback). Only Geidea can close this (a separator or a signed order number). The time stamp check assumes Geidea sends `11/27/2026 07:55:01`-style or ISO 8601 stamps; any other shape makes the guard ask Geidea's API first (up to 5 s more before the reply).
- **Anyone can POST to the callback URL.** Such requests never change an order. They are noted as "Unverified Geidea callback" (max 3 notes per order, no free text from the request), kept on their own lines in the admin box, and logged at most 60 times an hour, so they cannot hide or replace Geidea's own callbacks.
- **Scheduled checks are not capped site-wide:** each Geidea order can cause 4 API calls (one per scheduled check, fewer once it is paid), in addition to at most 3 thank-you page lookups per order and 60 per hour on the site.
- The `wp_php_error_args` filter (used to keep the fatal error WordPress's handler saw) is WordPress core code that is not in the local source copy; without it, the recorder still reads `error_get_last()` first, before any other shutdown callback.
- Geidea's own handler runs after the plugin completed the order and calls `woocommerce_pre_payment_complete` and `woocommerce_payment_complete` a second time (it always did, once). No status hook or email fires again; stock is reduced only once per order (WooCommerce keeps a per-order "stock reduced" flag; that code is not in the local source copy). Geidea's handler has no amount check of its own, so when a signed "paid" callback does not match the order (amount, currency, site, Geidea payment already on another order) the plugin stops that handler for the request and WooCommerce answers 400; the order is left unpaid and the note says why.
- When Geidea's callback names an order number that does not exist, Geidea's handler stops with a PHP fatal error (500); the log line shows it (seen in the local test with a copy of its code).
- The thank-you page check can delay that page by up to `geidea_lookup_timeout` (10 s) when Geidea's API is slow, once per order every 20 s.
- Scheduled checks need WP-Cron / Action Scheduler to run. They stop after 120 minutes; later, use the order action.
- Two paid Geidea payments for one order (two Place order clicks, both paid): the order is completed with the first and a note asks to check for a double charge.
- An order that was paid once and later set to cancelled, failed or on-hold by hand is never completed again by the plugin, and a cancelled order older than `geidea_max_age_days` (7) is only reported, not completed.
- The payment lock has the same residual case as the referral lock (two requests clearing a stale lock at the very same moment). The order is read again inside the lock and carries `_lp_geidea_paid` once completed, which keeps a second completion out in every other case. With HPOS's optional "data store caching" feature (off by default) a re-read could still come from cache; the site does not use it as far as known.
